# Agent Note: انتظار ترتيب توجيه النظام قسم مقطع حسب تنشيط ترتيب تصيير

Status: implemented
Archived: 2026-08-25

[English](2026-08-24-system-prompt-section-order-ties.md) | العربية

## Problem

`SystemPromptRegistry` استخدام مستقر ترتيب ترتيب حسب `order` ترتيب صف قسم مقطع، لذلك نفسه order قسم مقطع سوف حسب إضافة تنشيط ترتيب تصيير.`tool:cordis` و `tool:workflow` كل إعلان `order: 115`، لكن اثنان من في مختلف منصة كل جديد تركيب في تنشيط ترتيب مختلف. لذلك،ACP(Agent Client Protocol) و SDK لقطة إعادة تشغيل ممكن يأخذ نفسه قسم مقطع تجميع صار مختلف في قد إيداع `system-prompt.expected.md` ملف ترتيب.

## Decision

في لا تغيير قائم متبادل مقابل ترتيب قبل رفع تحت، لـ تلقي أثر قسم مقطع تسلسل إشارة تحديد متبادل لا نفسه order:`tool:cordis` إبقاء 115،`tool:workflow` استخدام 115.5،`tool:ralph` إبقاء 116، يمكن متابعة تشغيل فرعي بديل إدارة إشارة جذب إبقاء 116.5، فرعي بديل إدارة تقرير إبلاغ إشارة جذب إبقاء 117. نص التوجيه نص و أداة schema إبقاء ثابت.

## Alternatives considered

**في لقطة harness في مواصفة تحويل قسم مقطع ترتيب.** قد مرفوض، لأن وقت التشغيل، طلب علامة رأس و نموذج نص التوجيه ما زال تلقي تنشيط وقت ترتيب أثر، فقط لديه fixture مقارنة مقارنة سوف إخفاء فرق مختلف.

**في سجل التسجيل في استخدام قسم مقطع اسم ضرب كسر و صف.** قد مرفوض، لأن هذا سوف ساكن صامت إعادة ترتيب كل واحد مجموعة قائم و صف. صريح order يجعل كل نموذج مرئي موضع كل من مساهمة هذا قسم مقطع إضافة حينئذ أرض قرار.

## Consequences

Cordis و workflow إشارة جذب أداة لديه لا اعتماد منصة ترتيب، معا Ralph ما زال ترتيب في يمكن متابعة تشغيل فرعي بديل إدارة إشارة جذب و فرعي بديل إدارة تقرير إبلاغ إشارة جذب قبل. حاجة مستقر متبادل مقابل موضع نص التوجيه قسم مقطع يجب استخدام متبادل لا نفسه `order`؛ أخرى انتظار ترتيب قسم مقطع ما زال اعتماد تنشيط ترتيب، لا يخص هذا قرار نطاق.

## Testing

بلا مفتاح ACP و SDK لقطة إعادة تشغيل سوف ثابت Cordis ترتيب في workflow قبل، و إبقاء workflow،Ralph، يمكن متابعة تشغيل فرعي بديل إدارة و فرعي بديل إدارة تقرير إبلاغ إشارة جذب ترتيب. كامل لقطة طقم عنصر تحقق تحديث جديد fixture.
