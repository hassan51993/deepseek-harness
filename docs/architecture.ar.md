# معمارية DeepSeek Harness

[English](architecture.md) | العربية

اقرأ هذا قبل تغيير أي شيء تحت `packages/`. وهو يفترض أنك تعرف Cordis؛ فإن لم تكن تعرفه فابدأ بـ[المدخل](cordis-primer.ar.md) أو [الدرس](cordis-tutorial/index.ar.md).

ونوصي باستعمال agent لاستكشاف الشفرة وفهم معماريتها.

## Cordis

[Cordis](cordis-primer.ar.md) هو الإطار الذي يقوم عليه dsh: تسهم الإضافات بخدمات وأحداث منمَّطة وآثار قابلة للعكس في سياق مشترك. وكل جزء من المنتج إضافة، بما في ذلك مهايئ النموذج وregistry الأدوات وسجل الجلسة وagent loop نفسها، فكلٌّ منها قابل للاستبدال من الإعداد.

ولا توجد نواة ذات امتياز تُرقَّع: فأنت توسّع dsh بتركيب إضافة بجوار الأخريات، والتسجيلات آثار تنفكّ حين تُفرَّغ إضافتها.

## الـ profiles وحزم التركيب

`dsh` العامل شجرةُ إضافات تُركَّب عند الإقلاع من طبقات مرتّبة.

الـ **profile** تركيبٌ مسمّى يُخزَّن في دليل Harness المنزلي. وهو يعدّد حزم التركيب التي يكدّسها، ويحمل ما يثبّته من إضافات خارج الشجرة، ويحفظ `cordis.patch.yml` الخاص بالمستخدم. وتُشحن `web` و`headless` و`sdk` و`sdk-minimal` و`acp` قوالبَ جاهزة.

و**حزمة التركيب** صيغة توزيع لصفوف إعداد Cordis وللشفرة التي تركّبها، فيبقى ما تدرجه قابلًا للترقيع من الطبقات فوقها.

ويعلن كلٌّ منهما عن نفسه في `package.json` الخاص به تحت الحقل `dsh`: فـ `dsh.profile` يعدّد حزم تركيب الـ profile، و`dsh.bundle` يشير إلى ملف patch الخاص بحزمة التركيب.

و[`dsh-base`](../packages/bundle/base/README.ar.md) هي الطبقة الأولى المشتركة في الـ profiles `web` و`headless` و`sdk` و`acp`: مهايئات النماذج، والأدوات، والحفظ الدائم، وسياسة البيئة المعزولة والموافقة، والإعدادات، والاعتمادات، والقياس عن بُعد. وتضيف [`dsh-web-app`](../packages/bundle/web-app/README.ar.md) تطبيقَ المتصفح، وتضيف [`dsh-headless`](../packages/bundle/headless/README.ar.md) مشغّلًا لتشغيلة واحدة بلا خادم، وتضيف [`dsh-sdk-app`](../packages/bundle/sdk-app/README.ar.md) خادمَ JSON-RPC الخاص بـ SDK، وتضيف [`dsh-acp-app`](../packages/bundle/acp-app/README.ar.md) خادمَ ACP المخصص للأتمتة وحدها. أما [`dsh-sdk-minimal`](../packages/bundle/sdk-minimal/README.ar.md) فاستثناء مقصود: حزمة تركيب واحدة تملك شجرة SDK الصريحة كاملةً ولا تطبّق `dsh-base`.

وتُطبَّق الطبقات على قائمة مداخل فارغة بهذا الترتيب: كل حزمة تركيب بترتيب تعدادها في الـ profile، ثم `cordis.patch.yml` الخاص بالـ profile، ثم الذي على مستوى الدليل المنزلي، ثم أي طبقة `--patch`. والـ patch يقصد صفًّا بمعرّفه فيستبدل إعداده كله، أو يدرج صفوفًا جديدة.

ويتحكم YAML في HMR: فـ base تفعّل `dsh-hmr` للإعداد وحده؛ وheadless وSDK وACP تعطّله؛ و`sdk-minimal` لا تتضمنه. وتتجاوز patches الـ profile هذه الافتراضات. وينسّق HMR المراقبةَ وإعادةَ التحميل؛ ويوفّر المُقلِع بياناتِ الـ profile والجاهزية.

وتتضمن base [مدير الإضافات](../packages/boot/plugin-manager/README.ar.md) من أجل Web والوكلاء.

ولترى الشجرة التي يقلعها جهازك:

```sh
dsh --profile web --dump-config
```

وأي صف يطبعه يمكن استبداله بـ patch من عندك.

وآليات التركيب في [app-boot](../packages/boot/app-boot/README.ar.md#profiles)؛ وحقول الإعداد في [دليل الإعداد](config-catalog.ar.md) المولَّد.

## إقلاع التطبيقات

تطبيقات Node المدعومة تُقلَع عبر profiles مسمّاة من `dsh`. والـ profiles المشحونة هي `web` و`headless` و`sdk` و`sdk-minimal` و`acp`، وتُختار بـ `dsh --profile <name>` أو `dsh <name>`. والاسم `plugin` يسمّي أمر الإدارة، فـ profile بهذا الاسم يشترط `--profile plugin`. ويحلّ TypeScript SDK اعتماديتَه على `dsh` بالإصدار نفسه ويختار `sdk`؛ ويبقى تركيب الإضافات المخصص profile مع ملفات patch مرتّبة، لا ملفًّا تنفيذيًا آخر ولا شجرةَ تطبيق مضمَّنة. و`sdk-minimal` حزمة تركيب مستقلة يملكها المستودع خلف المُقلِع نفسه، لا شجرة Cordis يوفّرها المستدعي.

أما واجهات الأوامر المستنسخة، والملفات التنفيذية الخاصة بالبناء أو الاختبار وحدهما، وتركيبُ الإضافات مباشرةً داخل العملية، ومعاينةُ WebWorker الخاصة في المتصفح، فليست مُقلِعات تطبيقات للإطار. ويُبقي [`verify-application-entrypoints`](../scripts/verify-application-entrypoints.ts) كلَّ `bin` حزمة وكل مصدر تنفيذي وكل عرض في الجذر ضمن صنف صريح، ويرفض أي مسار تطبيق Node يتجاوز `dsh`.

ويتبع Python SDK معمارية التطبيقات نفسها. فعجلةُ وقت تشغيله تحزم واجهة `dsh` العادية باسم `deepseek-harness-sdk-runtime-<platform>-<arch>`، ويُقلع العميل `dsh --profile sdk` بدليل منزلي صريح للإطار افتراضيًا. ويختار المثال الأدنى الـ profile المشحون `sdk-minimal`. ويكشف Python اختيارَ الـ profile وملفاتِ patch المرتّبة بدل شجرة Cordis كاملة؛ وتُثبَّت الإضافات الخارجية الدائمة عبر `dsh plugin`. أما حامل الإعداد المباشر الخاص الذي أُزيل فلا `bin` توافق له ولا محلّل احتياطي.

## تطبيق سطح المكتب

يحمل [تطبيق سطح المكتب بـ Electron](../apps/desktop/README.ar.md) وقتَ تشغيل dsh الإنتاجي بعينه في موارد موقَّعة، ويملك المسار المحجوز `$DSH_HOME/profiles/desktop`. وتهيّئ مساعدات الـ profile المشتركة ملفاتِه، وتوفّق بين حزم التركيب المثبَّتة، وتحلّ اعتماديات التثبيت وحزم التركيب دون أن تستبدل الحزم التي يملكها pnpm. ويتشارك CLI وسطح المكتب بياناتِ المنتج، بينما تبقى الحزم التنفيذية وخيارات التفعيل وملفات القفل منفصلة. ولا يستطيع CLI العام إدارة profile سطح المكتب.

ويُقلع Electron مضيفَ سطح المكتب الخاص في وضع Node الخاص بـ Electron. ويستدعي المضيف مشغّلَ profiles المشترك في CLI وتطبيقَ Web كاملًا. وتحمّل النافذة فورًا أصولَ Web المحزَّمة وتنتظر حقن الإقلاع قبل تفعيل إضافات العميل في الوثيقة نفسها. ويملك Web الـ RPC والتدفقات؛ ويصل حامل سطح المكتب الصفحةَ المحلية بالمضيف المستوثَق. ويحمل IPC في Node حقنَ الإقلاع والجاهزيةَ والأعطالَ القاتلة والإغلاق. ويستعمل سطح المكتب المنفذ `19387` افتراضيًا، ويستطيع إعداد الـ profile تجاوزه. وتشغّل واجهةُ المستخدم التي يملكها الغلاف معاملاتِ الإضافات عبر pnpm المحزَّم بإعداد المستخدم والـ profile المعتاد.

## الأحداث

الأحداث هي نقاط الامتداد، واختيار المجال الصحيح هو القرار الأول في معظم التغييرات.

- **أحداث الجلسة** وقائع دائمة تُلحَق بالسجل وتُذاع عبر `session/event`. استعمل واحدًا منها حين يجب أن تنجو الواقعة من إعادة التحميل.
- **أحداث الـ agent** (`agent/*`) تحمل `Agent` حيًّا: صندوق الوارد، والخطوة، والحالة، والطلب، والتحقق، والمتابعة. استعمل واحدًا منها لمراقبة العمل الجاري أو اعتراضه.
- **أحداث القدرات** تلحق السياساتِ والمهايئات بـ seam (`fs/*` و`tools/*` و`telemetry/*`) دون استيراد الحلقة.

وتنتظر AgentLoop تهيئةَ `agent/created` المتسلسلة قبل بدء العمل المصطفّ. وفشل التهيئة يتراجع عن الإنشاء؛ ويعرّف [agent-loop](../packages/core/agent-loop/README.ar.md#understand-the-implementation) ترتيبَ التفكيك.

وتعدّد [خريطة الأحداث](event-producer-consumer.ar.md) منتجي كل حدث ومستهلكيه.

## مسار الجولة

**الخطوة** طلبُ نموذج واحد مع الأدوات التي يستدعيها. و**الجولة** صفر خطوة أو أكثر: تُفتح قبل أن يُطالَب بأول مدخلاتها، وتُغلق متى لم يبقَ شيء مستحق.

```text
turn/start
  claim next-step input plus one queued message
  assemble prompt sections + tool schemas; project runtime context
  -> agent/pre-step                   reject | enter(messages, startsRequestSeries?)
     reject, or a first enter rewritten empty -> close the turn with no step
     step/start
     agent/request -> prepareCall (cancellation commits neither system nor users)
     reconcile system/message using the prepared call capability
     append entered messages as user/message; log request/header and request/context as needed
     derive and freeze model history from the log
     stream the bound prepared call -> llm/stream -> agent/assistant-stream start
       agent/assistant-stream chunk*
       assistant/message | assistant/attempt -> agent/assistant-stream end
     tool/call* -> tools/pre-execute -> tools/execute -> tools/post-execute -> tool/result*
     step/end
     tools owe another request, or next-step input arrived -> claim -> next step
  -> agent/turn-stopping
turn/end
```

والأحداث `turn/*` و`step/*` و`system/message` و`user/message` و`assistant/message` و`assistant/attempt` و`tool/*` أحداثُ جلسة دائمة؛ وما بقي نقاطُ امتداد حية في ثلاثة مجالات. وينشر `agent/assistant-stream` إطارَ بدء محليًا للعملية، وإطاراتِ قطع عابرة، وإطارَ نهاية. وتودع الحلقة التدفقَ المضغوط كاملًا رسالةً واحدة أو محاولةً تُسجَّل فقط، قبل إطار نهاية مودَع، ومهايئُ متابعة الجلسة في Web هو المستهلك البعيد الوحيد للحدث الحي. والأحداث `agent/pre-step` و`agent/request` و`llm/stream` وأحداث `tools/*` الثلاثة waterfalls، وعلى مستمعيها استدعاء `next()` للتفويض؛ أما `agent/turn-stopping` فمتسلسل ولا `next()` له.

وصندوق وارد واحد يغذّي المشغّل؛ والسياق المحقون ينتظر رسالةً توقظه. وتكشف إسقاطةُ `inbox` الدائمة في AgentLoop المدخلاتِ المعلّقة بلا وكلاء أحياء.

ويقرّر `agent/pre-step` المدخلاتِ المقبولة. وللمستمعين أن يعيدوا كتابة الرسائل المطالَب بها أو يرفضوها؛ والمطالبة الأولى المرفوضة أو الفارغة تغلق جولةً دائمة بلا خطوة. وقد يضبط قرارُ الدخول القيمةَ `startsRequestSeries`: فتسجّل الحلقة `request/header` جديدًا (بالسبب `series`، أو `change` مع `startsSeries: true` حين يتغيّر المغلّف أيضًا). والمستمعون اللافّون يحفظون ذلك الإعلان بـ `{ ...decision, messages }`. وبعد التجميع و`step/start`، يحلّ `agent/request` و`prepareCall()` المسارَ الفعلي قبل إيداع توجيه النظام والرسائل المقبولة؛ والإلغاء أثناء أيٍّ من الطورين اللاتزامنيين لا يودع شيئًا منهما. وقدرةُ الاستدعاء المحضَّر تحكم قبولَ التوجيه، لا `request/context` السابق له. وكل محاولة توفّق تزامنيًا التجميعَ المصيَّر نفسه، ولا تُلحق الرسائل إلا في المحاولة الأولى، وتسجّل الترويسة والسياق عند اللزوم، وتشتق تاريخ الطلب وتجمّده قبل بث الاستدعاء المربوط. ولا تعيد المحاولاتُ التجميعَ ولا `agent/pre-step`. واستبدالُ السطوح وقراراتُ إزاحة الصور بعد الإرفاق تبدأ سلسلةَ طلبات جديدة، ومن ذلك أثناء أول خطوة تمهيدية بعد الاستئناف؛ أما الاستئناف بلا تغيير فيتابع السلسلة. وتحجز أول خطوة مقبولة رأسَ النظام قبل رسائل المستخدم حتى مع توجيه فارغ (بلا رسالة على السلك). ولا يسافر التوجيه إلا تاريخًا في `system/message`: فالتصيير الفارغ يمسح كل عُقد النظام النشطة، فلا يبقى توجيه قديم يراه النموذج؛ والمسارات القادرة تستطيع إلحاق تحديثات غير فارغة بعد البادئة المخزَّنة؛ أما المسارات غير القادرة وسلاسل الطلبات الجديدة فتجمّع نص التوجيه غير الفارغ عند عقدة النظام الأولى، مع تسجيل استبدالات فارغة لعُقد النظام اللاحقة غير الفارغة ([القرار](../.agents/notes/implemented/architecture/2026-09-02-system-prompt-as-surface-node.ar.md)؛ [قاعدة القرار](../packages/core/agent-loop/README.ar.md#understand-the-implementation)).

وترسل الحلقة طلبات غير قابلة للتغيير مع إبقاء الإلغاء حيًّا. ولا تعيد استعمال دليل تجميد الرسائل إلا للهويات التي جمّدتها كاملةً؛ ويملك [agent-loop](../packages/core/agent-loop/README.ar.md) قواعدَ بناء الطلب.

التفاصيل: [مخطط التسلسل](agent-lifecycle.ar.md)، و[خط معالجة الأدوات](tool-execution-pipeline.ar.md)، و[الإلغاء والتعافي من الأخطاء](subsystems/core.ar.md#the-agent-handle).

## سجل الجلسة

سجل الجلسة هو مصدر السياق الذي يراه النموذج. وتُسقط منه `deriveMessages()` تاريخَ النموذج. وكل `assistant/message` تضمّن التدفقَ المضغوط الموقوت بعينه الذي أنتج محتواها المجمَّع؛ ويحتفظ `assistant/attempt` بالمحاولات المستقرة الفاشلة والمعادة والملغاة وذات أخطاء التدفق، دون أن يضيف إلى تاريخ النموذج. والتفريع والاستئناف ونصوص المحادثة والقياس عن بُعد والحفظ الدائم كلها تشتق من هذه التسويات الدائمة، بينما تأتي تدرّجية واجهة المستخدم الحية من `agent/assistant-stream`؛ وفقدُ العملية فقدًا قاسيًا قبل التسوية لا يخلّف تدفقَ محاولة دائمًا ([القرار](../.agents/notes/implemented/architecture/2026-09-01-v2-embedded-assistant-streams.ar.md)).

ولا يعرف مستهلكو الجلسة إلا الصيغة المنطقية الحالية. فـ `stat` و`list` المقصوران على الترويسة يعيدان مسح كل دليل جلسة، ويختاران أعلى جيل معياري فيه عدديًا، ويترجمان ترويسةً تاريخية مدعومة دون تحميل الأحداث ولا نشر خَلَف. أما `open` لجلسة مخزَّنة فيختار الجيل نفسه، أو يرفض إصدارًا مستقبليًا، أو يفكّ ويركّب سلسلةَ الترحيل الساكنة المتجاورة مرةً واحدة قبل أن يعيد أحداثًا منطقية حالية متحقَّقًا منها. و`open` للقراءة يستعمل تلك النتيجة في الذاكرة بلا نشر خَلَف؛ أما `open` للكتابة فيرمّز أولًا ويتحقق وينشر حصريًا الخَلَفَ النهائي المسمّى بإصداره بجوار المصدر الذي لا يتغيّر. ويبقى الإصلاح المعتاد لذيل مقطوع غير مختوم مسؤوليةَ مستهلك المقبض؛ ولا يدرج الترحيل `turn/end` مقطوعًا مفقودًا إلا في حالة إعادة التشغيل المُصدَرة المحدودة التي ختمها `turn/start` لاحق. ويستعمل JSONL في v0 الاسمَ `session.jsonl[.zstd]`، ويستعمل v1 وما بعده `session.vN.jsonl[.zstd]` بحروف صغيرة، ولا تُعاد تسمية مسارات الأجيال المودَعة ولا تُستبدل ولا تُحذف أبدًا. ويملك مزوّد JSONL التأطيرَ الفيزيائي والضغطَ واختيارَ الجيل والنشرَ الحصري، بينما تملك كل حزمة ترحيل متجاور خطوةً واحدة بالضبط من `vN` إلى `vN+1` ([القرار](../.agents/notes/implemented/architecture/2026-08-31-released-session-format-migrations.ar.md)).

**ما يراه النموذج مسجَّل.** فكل ما يصل إلى طلب نموذج يجب أن يكون قابلًا لإعادة البناء من السجل، ويؤكّد ذلك ثابتٌ في وقت التشغيل. والمدخل الجديد الذي يراه النموذج يشترط حدثَ جلسة. والإضافات التي تغيّر محتوى رسالة قائمة تسجّل [إسقاطات رسائل خالصة](subsystems/session.ar.md#plugin-owned-message-projections)؛ ويوفّر القرّاء المنفصلون التعريفاتِ نفسَها صراحةً.

**seam الإسقاط.** تملك `dsh-session-projection` المفتاحَ `ctx.sessionProjections`: فالوحدات المسجَّلة تطوي الأحداثَ المودعة تدريجيًا، ويقرأ مستهلكو المضيف حالةً منمَّطة واحدة بـ `stateOf()`، وتجمّع الحواملُ عروضَ العميل المقصوصة بـ `snapshot()`. وقارئ المضيف إما أن يشترط هذه الخدمة عند التفعيل وإما أن يفشل صراحةً عند غياب الـ registry أو المفتاح المطلوب. وللمساهمين أن يبقوا على تسجيل `ctx.inject(['sessionProjections'], ...)` دون أن يضعوا قيمةً افتراضية صامتة لقيمة مضيف مفقودة. وتسجّل agent loop حالةَ `turnBoundary` المشتركة لقرّائها ([القرار](../.agents/notes/implemented/architecture/2026-08-19-session-projection-mandatory-seam.ar.md)).

## seams القدرات

الـ **seam** قدرةٌ قابلة للاستبدال ذات ثلاثة أدوار: **Service Definition** تعلن الواجهة، و**Service Provider** ينفّذها، و**Consumer** يستعملها، وهو غالبًا أداة موجَّهة إلى النموذج. وقد تجمع الحزمة أدوارًا، لكن الدور وحده ليس seam؛ وإضافة قدرة تعني تصميم الأدوار الثلاثة ([خريطة القدرات](capability-seams.ar.md)).

والـ seams هي سبب أن استبدال مزوّد واحد يغيّر المنتج كله. فمزوّدو نظام الملفات والعمليات الفرعية يتشاركون عالَم تنفيذ واحدًا، فتوجيههم إلى بيئة معزولة بعيدة ينقل Bash وPTY وLSP معهم، بلا تفريعٍ للمزوّدين. و[مزوّدو subagent](subsystems/subagent.ar.md) يتنوّعون بالقدر نفسه خلف واجهة واحدة، من agent ابن جديد إلى جولة مفوَّضة في منتج آخر.

و[فرق الوكلاء التجريبية](subsystems/agent-team.ar.md) هي seam تنسيق منشورة تُفعَّل اختياريًا على `ctx.agentTeams`، بقائمة أعضاء دائمة ولوحة مهام وصندوق بريد فوق وكلاء فرعيين قابلين للمتابعة.

## أين يذهب السلوك الجديد

السلوك الجديد يلحق بنقطة امتداد موثَّقة. وتغييرُ الحلقة نفسها يحدّث هذه الخريطة.

| الهدف | الآلية |
|---|---|
| إضافة مزوّد نماذج | سجّل مهايئه على `ctx.llm` |
| إضافة قدرة موجَّهة إلى النموذج | سجّلها على `ctx.tools`؛ وينضم schema الخاص بها إلى تجميع التوجيه |
| إعطاء جلسة واحدة مجموعةَ قدرات مختلفة | ركّب agent preset؛ وصفُّ الخدمة هناك يحتاج مجالَ `isolate` |
| إضافة تنفيذ shell | سجّل خلفية `ctx.shell`؛ والمحلية تُقلع عبر `ctx.subprocess` |
| إضافة تنفيذ في طرفية دائمة | سجّل خلفية `ctx.terminals` مع `dsh-tool-terminal` |
| إضافة أمر للإنسان | سجّله على `ctx.commands`؛ ويُوزَّع بلا جولة نموذج |
| إضافة عمل في الخلفية | سجّله على `ctx.jobs`؛ وأدوات `job_*` تجمعه أو توقفه |
| بدء جلسة من webhook خارجي | سجّل قاعدةً موثوقة على `ctx.webhookRuntime` وركّب مهايئ مزوّد |
| إضافة وصول إلى نظام الملفات أو سياسة له | سجّل مزوّد `ctx.fs` أو استمع إلى أحداث `fs/*` |
| حصر العمليات المُقلَعة | استعمل خلفية `ctx.sandbox`؛ ويلفّ المستهلكون argv قبل الإقلاع |
| اعتراض طلب أو أداة أو جولة | استعمل حدث `agent/*` أو `tools/*` الخاص بها؛ و`agent/turn-stopping` يوقف جولة |
| إضافة سياق يراه النموذج | استدعِ `agent.inject()`؛ فيصل في الطلب المقبول التالي |
| إضافة تكامل مع واجهة أو محرّر | قُد `ctx.agents` وصيّر من `session/event` |
| إضافة عقدة محادثة في عميل Web | سجّل `ConversationNodeDefinition` ومصيّرًا مفهرسًا |
| إضافة حالة جلسة دائمة | وسّع `SessionEventMap`؛ وصيّر وأعِد التشغيل من السجل |
| توليد عناوين الجلسات | سجّل مزوّد `ctx.sessionTitle` الوحيد |
| إدارة غاية داخل الجلسة نفسها | استعمل `ctx.goals`؛ وتابِع عبر `agent/*` |
| تفريع جلسة عند حدّ جولة | `ctx.agents.create({ sessionId, seed, meta: { parentSession, seedLength } })` — ولا تدوم إلا الجلسات التي نشرتها agent loop |
| تخزين الجلسات في خلفية جديدة | نفّذ `SessionPersistence` (`create` و`open` و`stat` و`list` و`export`) فوق سقالة المقبض المشتركة |
| حصر تسجيل في agent واحد | استعمل `agent.ctx` الخاص بذلك الـ agent |

ويربط [دليل التوسعة العملي](cookbook/extension-cookbook.ar.md) الميزاتِ بالقدرات، ويفهرس الأدلة خطوةً خطوة لـ[الحزم](cookbook/adding-a-package.ar.md) و[الأدوات](cookbook/adding-a-tool.ar.md) و[مهايئات LLM](cookbook/adding-an-llm-adapter.ar.md) و[بطاقات الإعدادات](cookbook/adding-a-settings-card.ar.md). ويملك [نظام المحادثة الفرعي](subsystems/conversation.ar.md) تجميعَ عُقد المحادثة.
