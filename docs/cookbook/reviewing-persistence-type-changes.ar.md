# دليل عملي: مراجعة تغييرات أنواع الحفظ الدائم

[English](reviewing-persistence-type-changes.md) | العربية

## الملخص

استعمل هذا الدرس بعد تغيير نوع حفظ جلسة معلَن، في نسخة عمل مساهِم مثبَّتة الاعتماديات. قدّم شرحَ توافق ثنائي اللغة، ثم دع أمرًا واحدًا يصنّف التغيير ويولّد سجلاته. ويشرح [مرجع السجلات](../persistence-changes/README.ar.md) الملفاتِ والقواعدَ التلقائية. وتسكن كل مدخلات المقارنة في نسخة العمل؛ فلا يلزم فرعٌ أساس ولا وصول إلى الشبكة.

<a id="generate"></a>
## اختياري: افحص التغيير

لمعاينة قبل التسجيل، شغّل من جذر المستودع:

```sh
pnpm --silent run verify-persistence-changes --json
```

استعمل `--silent` حين تستهلك JSON: فـ pnpm يُلحق نصَّ فشل دورة الحياة بالخرج القياسي لولا ذلك. والأوامر الفاشلة تخرج بالرمز 1 على كل حال.

اقرأ الجذرَ والمسارَ وصنفَ التغيير واشتراطَ الإصدار المبلَّغ عنها. والنوع المشار إليه قد يؤثر في عدة بصمات أحداث؛ فافحص كل جذر متأثر. وحتى يغطي التاريخُ schemas الجديدة يفشل التحقق. والجردُ المولَّد البائت يُفشِل التحقق أيضًا؛ وأمرُ التسجيل يحدّثه. وإن كانت `changes` فارغة بعد إعادة ترتيب حقول أو بدائل اتحاد، فشغّل `pnpm run gen-persistence-catalog` وأعِد الفحص. والبصمةُ غير المتغيّرة لا تحتاج تأكيدًا جديدًا، حتى حين تنتج التصريحاتُ المنسوخة أو مواضعُ المصدر فرقًا في الدليل.

<a id="acknowledge"></a>
## 1. سجّل التغيير

اكتب ملف JSON محليًّا يحتوي `en` و`ar`، ولكلٍّ منهما السلاسل `summary` و`compatibility` و`verification`. والمدخل التالي يصف تغييرَ حقل تدقيق خطاف من مطلوب إلى اختياري جرى تمرينه. استبدل الشرحَ ودليلَ الاختبار بوقائع تغييرك أنت؛ فواجهة الأوامر لا تثبت هذه الدعاوى.

احفظ المدخل في `.artifacts/persistence-change.prose.json`، وأنشئ الدليل المتجاهَل إن لزم:

```json
{
  "en": {
    "summary": "Makes the persisted hook audit decision optional.",
    "compatibility": "Existing records remain valid. Hook execution consumes HookOutput instead of replaying this audit field. Producers still write decisions, and absence does not imply pass.",
    "verification": "pnpm exec vitest run packages/hooks/hook-protocol/tests/events.spec.ts: 10 tests passed."
  },
  "ar": {
    "summary": "يجعل قرارَ تدقيق الخطاف المحفوظ اختياريًا.",
    "compatibility": "السجلات القائمة تبقى صالحة. وتنفيذ الخطاف يستهلك HookOutput بدل إعادة تشغيل حقل التدقيق هذا. ولا يزال المنتجون يكتبون القرارات، وغيابه لا يعني pass.",
    "verification": "pnpm exec vitest run packages/hooks/hook-protocol/tests/events.spec.ts: نجح 10 اختبارات."
  }
}
```

استعمل تاريخًا وسِمةً وصفية مكان معرّف المثال هذا:

```sh
pnpm --silent run persistence-changes --record 2026-09-11-poc-optional --prose .artifacts/persistence-change.prose.json --json
```

يتحقق الأمر من التاريخ ومن النثر المقترن، ويستنتج قرارَ الإصدار الأدنى، ويفحص أي زيادة مطلوبة في الترويسة قبل الكتابة. وهو يولّد زوجَ السجل، والملفَّ الكامل بعد schemas، والدليلين معًا، والجردَ الآلي، وسجلاتِ الاقتران. راجع الشروحَ وما يعود من `changes` و`roots` و`files` قبل الإيداع. وحذفُ `--prose` ينشئ مسودات غير مكتملة يرفضها التحقق حتى تُستكمل شروحها.

ويتبع الاستنتاجُ [قواعدَ التوافق الثابتة](../persistence-changes/README.ar.md#compatibility-rules)؛ وهو لا يغيّر المصدر ولا يخفّفها أبدًا. وإن لزم رفعُ إصدار، فاتبع أولًا [إضافة إصدار صيغة جلسة](adding-a-session-format-version.ar.md). وعلى السجل أن يتضمن انتقالَ `SessionHeader.version` المتزايد الخاص به؛ فرفعٌ تاريخي غير ذي صلة لا يأذن له. والتغييرات المعتادة لا تنشئ خطَّ أساس آخر أبدًا.

<a id="verify"></a>
## 2. افحص وأودِع وادفع

اختر فحوصَ سلوك المالك المتغيّر عبر [سياسة الاختبار](../testing.ar.md)، ثم شغّل فحوص التوثيق:

```sh
pnpm run doc-sync
```

يفحص `doc-sync` طزاجةَ جرد الحفظ الدائم ودليله، والتاريخَ كاملًا، والاقترانَ الثنائي اللغة. و`ok: true` من أمر التسجيل لا يغني عن هذه الفحوص ولا عن اختبارات سلوك المالك وترحيله. وتحتفظ حالاتُ فشل JSON بـ `ok: false` وبرمز تشخيصي في `code` وبرمز الخروج 1. وتتضمن التغييراتُ المبنيَنة أصنافًا ثابتة وبصمات قبل وبعد لكل جذر، فلا تحتاج الأتمتة إلى تحليل الأوصاف.

ويملك توليدُ السجلات دليلَه وأزواجَ سجلاته؛ أما تعديلات README حزمة أو أي صفحة ثنائية اللغة أخرى فتتبع مسار اقترانها المعتاد. راجع الفرقَ المقصود ورحّله، ثم أودِع وادفع كالمعتاد. وتبقى خطافاتُ الفحص والاقتران والمسافات على الملفات المرحَّلة، وفحصُ أنواع Host وClient قبل الدفع، سارية.

<a id="competing-records"></a>
## تحديث سجل لم يُقبَل بعد

إن تغيّر المصدر بعد التسجيل، فراجع شرحَ التوافق وحدّث السجلَّ الطرفي نفسه الذي لم يُقبَل بعد:

```sh
pnpm --silent run persistence-changes --update 2026-09-11-poc-optional --prose .artifacts/persistence-change.prose.json --json
```

يحدّث الأمر التصريحَ الآلي وschemas والدليلين والاقتران. وبلا `--prose` يحفظ الشرحَ القائم. ويرفض التحديثُ خطَّ الأساس الأول والسجلاتِ التي يعتمد عليها سجل آخر. ولا تستطيع الشجرة تحديدَ أي السجلات قُبل في المراجعة: فاحفظ التاريخ المقبول وأنشئ خلفًا بدلًا من ذلك.

وحين ينشئ الدمجُ سجلاتٍ طرفية متنافسة، حدّث السجلَّ غير المقبول مقابل التاريخ الباقي، ثم أعِد تقييم الفرق الناتج. وتأكيدُ جذر غير ذي صلة لا يحتاج تحديثًا. ويشرح [قرار الآلية](../../.agents/notes/implemented/process/2026-09-11-persistence-type-history.ar.md) لماذا تُحفظ اللقطاتُ الكاملة والأسلافُ لكل جذر.

ويبقى `--decision` الصريح دعوى مفحوصة. ففي تغيير نوع قيمة لخاصية قائمة، تفشل الدعوى الخاطئة عمدًا التالية قبل الكتابة:

```sh
pnpm --silent run persistence-changes --update 2026-09-11-poc-optional --decision same-version --json
```
