# دليل التطوير

[English](development.md) | العربية

يأخذ درس الإعداد المساهمَ الجديد من المتطلبات إلى نسخة عمل مفحوصة. ويغطي مرجع المساهمين بعده تخطيطَ المستودع، والعمل اليومي، وتنظيمَ CI. أما تبرير التصميم وتفصيل التنفيذ فيخصان Agent Notes والنصوص المرتبطة.

## درس الإعداد

### المتطلبات

- يدعم Node.js الإصدار 22.19 فما فوق و24 فما فوق. وتغطي CI الإصدارات 22.19 و24 و26؛ انظر [Agent Note عن أدنى إصدار لمحرك Node](../.agents/notes/implemented/process/2026-07-06-node-engine-floor.ar.md).
- pnpm مفعَّلًا عبر Corepack. ويثبّت المستودع `pnpm@11.7.0` في `package.json`؛ فشغّل `corepack enable` إن لم يتحلّل `pnpm --version` عبر Corepack.
- Git 2.26 أو أحدث؛ فإعداد الخطافات يفعّل امتداد Git للإعداد الخاص بشجرة العمل.
- اختياريًا: مفتاح DeepSeek API لعروض Web وheadless وأتمتة ACP، ولاختبارات e2e مقابل الواجهة الحقيقية.

### Windows وWSL 2

على Windows تستطيع التطوير بالأدوات الأصلية أو استعمال WSL 2 لبيئة Linux. وWSL 2 مفيد للتحقق من سلوك Linux ولاستعمال سلاسل أدواته حين يعوق تصريفُ الاعتماديات الأصلية أو أذوناتُ نظام الملفات التطويرَ على Windows. ولكل بيئة وقتُ تشغيلها وأدواتُ بنائها وأذوناتها؛ وWSL اختياري.

أبقِ نسخة العمل والاعتماديات المثبَّتة وسلسلة الأدوات في بيئة نظام التشغيل نفسها. ففي WSL 2 خزّن نسخة العمل في نظام ملفات Linux؛ ومع أدوات Windows الأصلية استعمل نظام ملفات Windows. فالوصول إلى الملفات عبر نظامَي الملفات يضيف كلفةً إلى العمليات الكثيفة على الإدخال والإخراج مثل Git وتثبيت الاعتماديات والبناء. انظر [إرشادات Microsoft عن تخزين الملفات والأداء](https://learn.microsoft.com/en-us/windows/wsl/filesystems#file-storage-and-performance-across-file-systems).

وثبّت الاعتماديات في كل بيئة على حدة، لأن الملفات الثنائية الأصلية والروابط قد تختلف بين أنظمة التشغيل. ونتائج الاختبارات تخص البيئةَ التي عملت فيها؛ ويبقى السلوك الخاص بـ Windows محتاجًا إلى تحقق على Windows الأصلي.

### الإعداد لأول مرة

ثبّت الاعتماديات من جذر المستودع:

```sh
pnpm install
```

ويهيّئ التثبيتُ أيضًا خطافات Lefthook المحلية لشجرة العمل، ومشغّلَ دمج Git باسم `dsh-translation-pairing`، عبر `scripts/install-lefthook.mjs`. ويملك [Agent Note عن الخطافات المحلية لشجرة العمل](../.agents/notes/implemented/process/2026-07-27-worktree-local-lefthook.ar.md) عقدَ سلامة مسار الخطافات؛ ويملك [Agent Note عن دمج الاقترانات التلقائي](../.agents/notes/implemented/process/2026-08-08-automatic-translation-pairing-merges.ar.md) مشغّلَ الدمج.

وإن غاب أي من التكاملين لأن الاعتماديات استُعيدت من الذاكرة المؤقتة أو تُخطّي `postinstall`، فثبّتهما يدويًا:

```sh
node scripts/install-lefthook.mjs
```

وإن رفض الغلاف إعدادَ Git القائم أو أبلغ عن قفل بائت، فاتّبع تشخيصه وAgent Note المرتبط بدل تعديل بيانات شجرة العمل الوصفية على غير هدى. وبعد نقل نسخة العمل، أعِد تشغيل الغلاف ليولّد المسار الذي يملكه من جديد.

وشغّل فحص الأنواع مرةً بعد الاستنساخ الجديد:

```sh
pnpm run typecheck
```

ويكتمل الإعداد حين يخرج `pnpm run typecheck` بنجاح.

### تخطيط مشروع TypeScript

يستعمل المستودع تجميعتَي Host وClient معزولتين. وتُسجَّل الحزمة العادية في تجميعة واحدة بالضبط: حزم Host في `tsconfig.host.json` وحزم Client في `tsconfig.client.json`؛ وتشير التجميعتان معًا إلى ثلاث حزم (`host/webserver` و`compaction/compaction` و`typert/registry`) بوصفها أوراقًا مشتركة، ليفحص كل جانب أنواعَ المصدر نفسه.

| الملف | الدور | يكوّن برنامجًا؟ |
|---|---|---|
| `tsconfig.json` | جذر الحل: `extends` للأساس، و`files: []`، وإشارات إلى التجميعتين. وهو مدخل اكتشاف tsserver، ومدخل التشغيل الصريح لرسم Project Reference كاملًا؛ وعبر `paths` الموروثة هو أيضًا إعداد التحليل لـ tsx حين يشغّل `scripts/`. | لا |
| `tsconfig.host.json` | تجميعة Host: حزم Host، والأمثلة، والاختبارات، والنصوص، والموقع، ومشروع Host الاستثنائي في `api/remotes`. | نعم |
| `tsconfig.client.json` | تجميعة Client: حزم `packages/client/*` واختباراتها، و`apps/web`، ومشروع Client الاستثنائي في `api/remotes`. | نعم |
| `tsconfig.base.json` | خيارات المصرّف المشتركة وخريطة `paths` للمصدر. وهو أيضًا واجهة التحليل التي توجّه إليها إعداداتُ vitest الأداةَ vite-tsconfig-paths: فلا `include` له، فتنطبق `paths` الخاصة به على كل مستورِد. | لا |
| `tsconfig.base.client.json` | إعدادات مصرّف المتصفح (`jsx`، ومكتبات DOM، و`types: []`) التي توسّعها تجميعةُ Client وكل حزمة `packages/client/*`. | لا |

وتبقى Host وClient برنامجَي تجميعة اثنين لأن الجانبين يدمجان تصريحَ واجهة `Context` في cordis تحت المفاتيح نفسها بخدمات مختلفة؛ وبرنامجٌ واحد يرى الدمجين يبلّغ عن تصادم. والتصادم لا يوجد إلا داخل `ts.Program`، ولا يثيره تحليل الوحدات أبدًا، ولهذا يجوز للحل أن يشير إلى التجميعتين، وتجوز لواجهة paths واحدة أن تغطي الجانبين. ويتبع ذلك ثلاثة انضباطات:

- لا يكتسب `tsconfig.base.json` أبدًا `include` ولا `files`: فهما يتسربان إلى كل مشروع حزمة يوسّعه، ويضيّقان نطاقَ المطابقة الشاملة للواجهة.
- والنص الذي يبني `ts.Program` على مستوى المستودع يبذر `tsconfig.host.json` أو `tsconfig.client.json` صراحةً، ولا يبذر جذر الحل أبدًا، لأن تسطيح التجميعتين في برنامج واحد يصادم دمجَي `Context`.
- والحزمة الجديدة تُسجَّل في تجميعة واحدة بالضبط؛ ولا تحمل إعدادَي ورقة إلا الحزمُ المقسومة أعلاه، وتُسجَّل الأوراق المشتركة في التجميعتين لأن على كل جانب أن يفحص أنواع المصدر نفسه. ووجودُ مدخل محمِّل Node ومدخل متصفح معًا ليس سببًا لقسمة حزمة؛ فإضافة Client العادية تنتج ناتجَي وقت التشغيل معًا في طور بناء Client.

وست حزم تقسم إعدادات Host وClient: `api/remotes` و`api/gateway` و`api/session-controller` و`api/workspace-controller` و`client/connection` و`session-query/session-log-export`. فمدخل Host في `api/remotes` يشارك في رسم Typert الخاص بـ Host، بينما يستورد مدخل Client تصريحات `/remote` المولَّدة؛ و`session-log-export` يُبقي إنتاج الأرشيف في Node خارج متحكّم المتصفح فيه. ولذلك فإن `tsconfig.json` في جذر كل حزمة مقسومة حلٌّ لا غير، وتشير التجميعتان والمستهلكون المباشرون إلى `tsconfig.host.json` أو `tsconfig.client.json` بحسب الجانب. وتمشي بوابة `constraints` في مساحة العمل على رسم Project Reference القابل للوصول، وتفحص وجهَ المصرّف لكل مشروع مشير: فالهدف ذو الإعداد الواحد يبقى صالحًا من أي وجه، أما الهدف المقسوم فعليه أن يسمّي الورقة المطابقة لا جذرَ حله ولا الورقة المقابلة؛ وتكتشف البوابة الحزمَ المقسومة من وجود إعدادَي ورقة معًا، فتنضم القسمة الجديدة إليها تلقائيًا. ويشرح [README الخاص بـ `api-remotes`](../packages/api/remotes/README.ar.md) و[README الخاص بـ `session-log-export`](../packages/session-query/session-log-export/README.ar.md) قسمتيهما.

ويتبع بناء الجذر ترتيبَ الاعتماديات المولَّد:

```sh
tsc -b tsconfig.host.json
tsdown --env.DSH_BUILD_FACE host
tsc -b tsconfig.client.json
tsdown --env.DSH_BUILD_FACE client
pnpm run build:web
```

ويستعمل مرورا tsdown مطابقةَ مساحة العمل الكاملة نفسها. فلا يمسحان نواتج البناء لاكتشاف حزم Client، ولا يصونان قائمةَ ترشيح لحزم Host وClient. وتختار إعدادات tsdown المحلية للحزمة مداخلَ الطور الحالي عبر `DSH_BUILD_FACE`: فإضافة Client العادية تنتج محمِّل Node وحزمة المتصفح معًا في طور Client؛ و`api-remotes` يستعمل `hostPhase: true` لينتج مدخل Host مبكرًا ولا ينتج في طور Client إلا حزمة المتصفح. ولا يستهلك tsdown إلا JavaScript الذي أخرجه طور tsc السابق إلى `lib/types`.

ولا يعمل Typert إلا أثناء tsdown الخاص بـ Host، مبذورًا بـ `tsconfig.host.json`. وهو يحلّل أنواع Host ويولّد نواتجَ الانعكاس الخاصة بـ Host وإسقاطَ Remote من Host إلى Client معًا؛ ولا يبدأ tsdown الخاص بـ Client تشغيلَ Typert. ولذلك يشغّل `pnpm run typecheck` طورَ مكتبة Host كاملًا قبل tsc الخاص بـ Client، بينما يمضي `pnpm run build` إلى tsdown الخاص بـ Client وبناءِ Web.

ويضمّن `pnpm run build` إصدارَ حزمة الجذر، وسبعةَ محارف من commit المصدر، وعلامةَ اتساخ حين يبلّغ Git عن تغييرات محلية؛ ويرث أيضًا قيم `DSH_CLIENT_*` الأخرى التي يوفّرها المستدعي. و`pnpm run build:official` هو المكافئ المحلي العابر للمنصات لبناء نواتج CI والإصدار، ويحذف علامة الاتساخ المحلية. وكل بناء كامل ناجح يكتب سجلًّا متجاهَلًا في Git يربط القيم العامة بعينها بخرج Vite وبحزم العميل الديناميكية؛ وترفض حزمُ الإصدار واختباراتُ Web المبنية سجلًّا مفقودًا أو نواتجَ غيّرها بناء جزئي لاحق. ولا يزال `pnpm run dev:web` يشترط شجرة النواتج من بناء كامل سابق، غير أنه يأخذ عيّنةً من الإصدار الحالي وحالة Git مرةً واحدة عند الإقلاع ويتشارك تلك البيئة مع كل أطوار المراقبة في الجلسة؛ وهو لا يتحقق من سجل البناء الكامل لأن أطوار المراقبة تعيد كتابة نواتجه المسجَّلة.

ويحلّ التحليلُ الساكن والاختبارات استيراداتِ مساحة العمل عبر خريطة `paths` الأساسية إلى `src`، وعليها أن تنجح على شجرة نظيفة؛ أما البوابات التي تستهلك خرج `lib/` المبني فتعلن تلك الاعتمادية صراحةً. وتصريحات Remote المولَّدة من Host إلى Client هي الاستثناء المقصود: فالأوامر العامة `typecheck` و`lint` و`doc-typecheck` تولّدها أولًا، بينما تفترض النصوص الداخلية `*:contracts-ready` أن أمرًا عامًا مستدعيًا أو بوابةَ مجدوِل تعتمد أصلًا على مرور توليد عقود Typert أو على البناء الكامل. انظر [ملاحظة ts-build-config](../.agents/notes/implemented/process/2026-06-17-ts-build-config.ar.md) لملكية الإخراج بـ tsc أولًا، و[ملاحظة Typert Remote](../.agents/notes/implemented/architecture/2026-08-02-typert-remote-method-calls.ar.md) لعقد تهيئة البوابات.

وتعلن خدمات الأعمال الطرقَ القابلة للاستدعاء على Host بـ `@Remote` أو `@RemoteScope`؛ ويولّد بناء Host أنواعَ Host إلى Client ومساهماتِ وقت التشغيل، ويحمّل تركيبُ `api-remotes` في Client تلك المساهمات تحت فضاءَي الأسماء `ctx.remote` و`agentCtx.remote` ذي النطاق. انظر [بوابة API](api-gateway.ar.md) للنواتج المولَّدة على الجانبين، وعلاقات تجميعها، والرجوع إلى SRC أثناء التطوير، وترتيب بناء Web.

وإن كان فحصٌ محلي ذو صلة يستهلك خرجَ حزمة مبنيًا، فابنِ مرةً أولًا:

```sh
pnpm run build
```

ويتضمن `pnpm run hygiene` أداةَ `publint` التي تتحقق من مداخل الحزم مقابل ملفات `lib/*.js` المبنية، و`verify-node-next-types` التي تتحقق من التصريحات المبنية مقابل مستهلك NodeNext مؤقت. وشجرةُ العمل الجديدة لا JavaScript محزَّمًا فيها ولا تصريحات حتى يعمل `pnpm run build`؛ ولا تشترط الإيداعات والدفعات العادية ذلك البناء إلا إذا استهلكته الفحوص المختارة لها.

### متغيرات البيئة

يقرأ مهايئ DeepSeek الحقيقي والعروضُ المعتمدة على مفتاح الاعتماداتِ من البيئة أو من ملف `.env` متجاهَل في Git في جذر المستودع:

```sh
DEEPSEEK_API_KEY=sk-...
DEEPSEEK_BASE_URL=https://... # optional
```

و`DEEPSEEK_BASE_URL` اختياري ويعود افتراضيًا إلى الواجهة العامة. ولا تودع اعتمادات حقيقية أبدًا. وتتخطى أجنحة e2e مقابل الواجهة الحقيقية نفسَها حين لا يكون `DEEPSEEK_API_KEY` مضبوطًا.

### تكاملات Git

يشتق مشغّلُ دمج الاقترانات سجلَّ `.i18n.yaml` المتعارض من blobs السلف والحالي والآخر المؤكَّدة، حين يستعمل ملفا اللغتين استراتيجيةَ Git النصية الافتراضية ويندمجان نظيفَين. وهو يفشل مغلقًا عند تعارض المالكين، أو عند إعداد دمج غير نصي، أو عند سجلات غير صالحة؛ وبعد دمج توقّف فعلًا، شغّل `pnpm run resolve-translation-pairing-conflicts` الذي يرحّل إلى منطقة التحضير كل سجل اقتران آمن ويخرج بحالة فشل إن بقيت تعارضات اقتران أخرى تحتاج عملًا يدويًا. انظر [عقد التوثيق الثنائي اللغة](i18n/README.ar.md#the-pairing-contract) للملفات والحالات التي يقبلها المشغّل بالضبط.

ويسبر المثبِّت مدخلَ مشغّل Node أو tsx بعينه قبل نشر إعداد شجرة العمل. فإن صار وقت التشغيل ذاك غيرَ متاح لاحقًا، كتب المُقلِع المستقل عن Node نتيجةَ Git النصية المعتادة، وترك الملف المرافق بلا حل، وطبع مسار التعافي؛ فاستعِد الاعتماديات وشغّل `pnpm run resolve-translation-pairing-conflicts`، أو شغّل `git merge --abort`. وإن رفض `pre-merge-commit` دمجًا نظيفًا فيما عدا ذلك، ترك Git النتيجةَ كاملةً في منطقة التحضير بلا إيداع؛ فأصلح العطل وشغّل `git commit`، أو أجهض. ويملك [Agent Note عن دمج الاقترانات التلقائي](../.agents/notes/implemented/process/2026-08-08-automatic-translation-pairing-merges.ar.md#failure-contract) حالاتِ الفهرس و`MERGE_HEAD` بالضبط.

ويُعَدّ lefthook في `lefthook.yml` نقطةَ تفتيش محلية سريعة:

- يتحقق `pre-commit` من سجلات الاقتران المرحَّلة مقابل blobs المالكين المرحَّلة، ويفحص الملفات المرحَّلة بملف الإعداد `.oxlintrc.staged.json` المستقل عن المشروع ويطبّق إصلاحات Oxlint بإعادة محاولة واحدة محدودة، ويعيد توليد `THIRD_PARTY_NOTICES.md` حين يكون ملف مرحَّل أحدَ مدخلاته، ويفحص الفرق المرحَّل بحثًا عن أخطاء المسافات، ويشغّل حارس بيان vendor.
- ويجري `pre-merge-commit` فحصَ الاقتران نفسه المعتمد على الفهرس قبل أن ينشئ Git إيداعَ دمج تلقائيًا.
- ويشغّل `pre-push` الأمرَ `pnpm run typecheck`، فيكمل طورَ مكتبة Host، بما فيه عقود Typert المولَّدة، قبل فحص TypeScript الخاص بـ Client.

ويتحقق حارس بيان vendor من أن التغييرات تحت `vendor/*/src` مرحَّلة مع تحديث البيان المقابل في `vendor/README.md`. انظر `vendor/README.md` قبل تعديل الشفرة المستنسخة.

وفيما عدا التحقق المحدود من السجلات المرحَّلة، لا تشغّل الخطافاتُ عمدًا اختباراتٍ ولا لقطاتٍ ولا فحوصَ توثيق ولا بناءً ولا نظافة. ويشغّل المساهمون [الفحوص المتصلة بالسلوك المتغيّر](../AGENTS.md#run-relevant-checks-locally) مرةً واحدة؛ وتملك CI التغطيةَ الشاملة واختباراتِ التحقق السريع للنواتج المبنية ومصفوفةَ التوافق مع Node 22.19 و24 و26.

ويستطيع المساهمون اختيارَ مجموعة البوابات المحلية الشاملة بـ `pnpm run check:all`. والأمر مستقل عن خطافات Git وليس تعليمةً للوكلاء.

### بوابات CI

يجمّع [سير عمل CI](../.github/workflows/ci.yml) الخالي من المفاتيح البواباتِ المستقلة في مسارات عريضة، ويشغّل إشارةَ توافق أصغر عبر إصدارات Node المدعومة. وينتظر مستهلكو النواتج بناءً واحدًا داخل مسارهم. وتعمل القياسات الإلزامية منفصلةً على Linux المستضاف من GitHub؛ ويملك [قرار مشغّل القياسات](../.agents/notes/implemented/testing/2026-09-06-standard-hosted-benchmark-runner.ar.md) التوجيهَ ومهلةَ المهمة. ويشغّل سير العمل المنفصل للواجهة الحقيقية الأمرَ `pnpm run test:e2e` بحدّ العمال المضبوط له. انظر [scripts/run-gates.ts](../scripts/run-gates.ts) وملفات سير العمل لجرد البوابات والمهام الحالي.

ولا تستعمل بروفاتُ تخطيط اعتماديات dsh وحزمِ dsh وvendor الخاليةُ من الاعتمادات مجمّعَ Linux المستضاف ذاتيًا القائم إلا حين يكون `DSH_CI_FAILOVER_LINUX=selfhosted` ويكون الحدث دفعًا موثوقًا إلى master أو طلبَ سحب من المستودع نفسه، غير متفرّع وغير صادر عن Dependabot. وكل الحالات الأخرى، ومنها التشغيل اليدوي، تستعمل `ubuntu-24.04`؛ ويبقى النشر اليدوي مستضافًا. انظر [قرار مشغّل بروفات الإصدار](../.agents/notes/implemented/process/2026-09-06-release-rehearsal-selfhosted.ar.md) لعزل المخزن الدائم وحدود الرجوع.

### الأوامر اليومية

تلخّص [تعليمات المساهمين](../AGENTS.md#commands) في الجذر الأوامرَ الشائعة، بينما يملك [`package.json`](../package.json) و[scripts/run-gates.ts](../scripts/run-gates.ts) جردَ النصوص والبوابات الحالي. اختر أصغر الفحوص التي تغطي السطح المتغيّر. وتغييرات التوثيق تستعمل `pnpm run doc-sync`؛ وتغييرات السلوك العام للحزمة تحدّث أيضًا README أو JSDoc المالك، وتشترط فحوصُ النواتج المبنية `pnpm run build` أولًا.

### تشغيل الـ profiles

شغّل بناء المستودع منفصلًا قبل استعمال هذه العروض من نسخة المصدر:

```sh
pnpm run build
```

ويحتاج وكيل البرمجة Headless ذو التشغيلة الواحدة إلى `DEEPSEEK_API_KEY` في البيئة أو في `.env` في جذر المستودع:

```sh
pnpm dsh --profile headless "summarize this workspace"
```

ويشغّل عرضُ وضع PTC الـ profile الخالي من الواجهة نفسه مع تفعيل عرض الشفرة:

```sh
pnpm run demo:ptc -- "summarize this workspace"
```

### وسوم TODO

استعمل أحد ثلاثة وسوم في التعليقات للإشارة إلى مشكلات معروفة في الشفرة، مرتَّبةً بالإلحاح:

- `FIXME`: مشكلة ينبغي أن تمنع إصدارًا جديدًا. ولا ينبغي أن يُشحن إصدار وفيه `FIXME` مفتوح، إلا أن يوافق المراجعون صراحةً على دمج التغيير رغم ذلك.
- `TODO`: مشكلة ينبغي إصلاحها قريبًا متى توفّرت الموارد.
- `XXX`: مشكلة قد نصلحها يومًا ما؛ وهي الأدنى أولويةً وبلا التزام.

اختر الوسم الذي يطابق الإلحاح، ليميّز كلُّ من يتصفّح الشفرة بين ما يمنع الإصدار وما قد يُؤجَّل إلى أجل غير مسمّى.

### توثيق الأنواع حرفيًا (`ts type-equiv`)

تلصق صفحات [الأنظمة الفرعية](subsystems/README.ar.md) تصريحاتٍ مكافئة للمصدر مع JSDoc الأصلي الخاص بها، ليرى القارئ تعريفَ النوع بعينه وعقدَ المصدر. ولكي لا ينحرف الملصوق حين يتغيّر المصدر، أحِطه بالسور ` ```ts type-equiv ` بدل ` ```ts `، وسجّله في `scripts/type-equiv.manifest.json` بملف المصدر والرمز الذي يعكسه:

```json
{ "doc": "docs/subsystems/session.md", "symbol": "SessionEvent", "source": "packages/core/session/src/types.ts" }
```

عندئذ يستخرج `pnpm run verify-type-equiv` (وهو جزء من `doc-sync`) تصريحَ ذلك الرمز وJSDoc الملحق به من المصدر عبر محلّل TypeScript، ويتحقق من مطابقة الكتلة لهما معًا. أما الصنف الذي لا تنتمي أجسام تنفيذه إلى الدليل، فاستعمل ` ```ts public-api ` واضبط `"projection": "public-api"`؛ فالإسقاط المفحوص يحتفظ بالحقول العامة والمُنشئ والوصولات والطرق وJSDoc الأصلي للصنف وأعضائه، ويحذف الأجسام والأعضاء الخاصة والمحمية. والمقارنة تتجاهل المسافات والتعليقات غير JSDoc، لكنها تشترط كل تعليق JSDoc أصلي، بما فيه توثيق الأعضاء، ليرى القارئ عقدَ المصدر بجوار تعريف النوع بعينه. وتُلزم البوابة بتناظر واحد لواحد بين الكتل الأصلية ومداخل البيان، بحسب الوثيقة والرمز والإسقاط؛ ولا تعيد كتلةٌ مقترنة في `.ar.md` استعمالَ مدخل شقيقها غير المُلحَق إلا حين يكون تسلسل الأسوار المتتبَّع كله مطابقًا بايتًا ببايت وبالترتيب نفسه. ويطبّق `doc-typecheck` قاعدةَ الاشتقاق نفسها على الأسوار القابلة للتصريف، مع استثناء نوعَي سور المكافأة للمصدر من التصريف ومن نسبة الانسحاب منه. وحين تغيّر تصريحًا موثَّقًا أو JSDoc الخاص به، تفشل البوابة حتى تحدّث الملصوق؛ وحين تضيف كتلة أصلية أو تحذفها، حدّث البيان في التغيير نفسه.
